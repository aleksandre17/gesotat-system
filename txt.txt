    62 +## Boundary rules
    63 +

    68 +- Archive Plane owns retention, legal hold and rollback history.
    69 +- API exposes only contract-approved metadata and signed URLs.
    70 +- Frontend never reconstructs physical paths and never reads MinIO directly.

  აბრუნებს მხოლოდ approved projection-სა და signed download-ს.

  ამ სიემაში რისი გაკეთება მიუწევს მომხრებეის? რა ცხირებში მუწევსჩანწერის გაკეთება? როგორ განისზრებაროვზე ფაილის მიბმა და როამდნი ფაიელი და რამდი კვაშირების?


• მომხმარებელმა ხელით უნდა შეავსოს მხოლოდ ბიზნეს-კავშირი; ტექნიკურ ნაწილს სისტემა ქმნის.

  ## მომხმარებლის მინიმალური სამუშაო

  Access პაკეტში საჭიროა:

  ### 1. ძირითადი row-ები

  __ent_<dataset>

  მაგალითი:

  {
    "source_entity_id": "row|1001",
    "name": "Record 1001"
  }

  სავალდებულოა ერთი სტაბილური key:

  source_entity_id

  ### 2. ფაილების აღწერა

  __raw_document

  მომხმარებელი უთითებს მხოლოდ:

  {
    "source_row_key": "file|1500",
    "original_filename": "report-001.xlsx",
    "source_primary_key": "report-001"
  }

  სისტემა თვითონ ამატებს:

  - checksum-ს;
  - byte size-ს;
  - MIME type-ს;
  - Object Storage URI-ს;
  - artifact ID-ს;
  - upload timestamp-ს;
  - parser/validation status-ს.

  ### 3. row ↔ file კავშირები

  რეკომენდებული generic relation:

  __rel_entity_artifact

  მომხმარებელი ავსებს:

  {
    "relation_key": "row|1001|file|1500",
    "entity_source_row_key": "row|1001",
    "artifact_source_row_key": "file|1500",
    "role_code": "SUPPORTING_DOCUMENT",
    "is_primary": true,
    "ordinal": 1
  }

  ეს არის ერთადერთი ცხრილი, სადაც განისაზღვრება კონკრეტულად რომელი ფაილი რომელ row-ს ეკუთვნის.

  ## რამდენი ფაილი შეიძლება ჰქონდეს ერთ row-ს?

  შეზღუდული რაოდენობა არ არის:

  ერთი row → ერთი ფაილი
  ერთი row → რამდენიმე ფაილი
  ერთი ფაილი → რამდენიმე row

  მაგალითად:

  row|1001 → file|1500
  row|1001 → file|1501
  row|1001 → file|1502

  ეს ნიშნავს, რომ row 1001-ს სამი attachment აქვს.

  ## რამდენი relation row არის საჭირო?

  relation row-ების რაოდენობა არის რეალური კავშირების რაოდენობა.

  მაგალითად:

  1000 business row
  1500 physical file

  არ ნიშნავს ავტომატურად 1,500 relation-ს.

  - თუ თითო row-ს ერთი ფაილი აქვს → 1000 relation;
  - თუ ზოგ row-ს რამდენიმე ფაილი აქვს → relation count მეტი იქნება;
  - თუ ერთი ფაილი რამდენიმე row-ს ეკუთვნის → თითო კავშირი ცალკე relation row-ია.

  ფორმულა:

  relation_count = რეალურად არსებული row ↔ file კავშირების რაოდენობა

  ## ყველაზე მარტივი რეჟიმი

  მომხმარებელი შეიძლება საერთოდ არ შეეხოს relation ცხრილს და ატვირთოს:

  dataset-package.zip
    ├── data.accdb
    └── files/
        ├── row-1001-report.xlsx
        ├── row-1001-photo.pdf
        └── row-1002-report.xlsx

  სისტემა filename/key წესით შექმნის:

  row-1001-report.xlsx → row|1001
  row-1001-photo.pdf   → row|1001
  row-1002-report.xlsx → row|1002

  უფრო საიმედო ვარიანტია manifest:

  {
    "attachments": [
      {
        "file": "files/row-1001-report.xlsx",
        "rowKeys": ["row|1001"]
      },
      {
        "file": "files/annual-report.xlsx",
        "rowKeys": ["row|1001", "row|1002", "row|1003"]
      }
    ]
  }

  ## მომხმარებელი რას არ ავსებს

  მომხმარებელს არ უნდა დასჭირდეს:

  - artifact_id;
  - object_uri;
  - bucket/object path;
  - checksum;
  - signed URL;
  - dataset_snapshot_id;
  - SQL;
  - ხელით generated relation IDs.

  ეს ავტომატურად იქმნება:

  filename/manifest
    → artifact identity
    → checksum
    → Object Storage object
    → relation validation
    → canonical locator
    → snapshot
    → API signed URL

  ამრიგად, მომხმარებლისთვის პრაქტიკულად საჭიროა მხოლოდ:

  1. ძირითადი row-ის stable key
  2. ფაილი
  3. row-სა და ფაილს შორის კავშირი

  ყველა დანარჩენი სისტემამ უნდა შექმნას, შეამოწმოს და დააკავშიროს.


  არის რამე კდიევ რაც ამ საეკთს ეხება და არ დასმულა?


  დიახ — რამდენიმე კრიტიკული საკითხი ჯერ ცალკე უნდა განისაზღვროს:

  ### Identity და კავშირი

  - რა არის row-ის immutable business key?
  - რა არის ფაილის logical identity?
  - შეიძლება თუ არა ერთი logical file-ის ახალი version?
  - როგორ განვასხვავებთ duplicate-სა და ახალ version-ს?
  - ერთი row-ს რამდენი primary/supporting/derived ფაილი შეიძლება ჰქონდეს?
  - შეიძლება თუ არა ერთი ფაილის მრავალ row-ზე მიბმა?
  - როგორ აღინიშნება is_primary და ordinal?
  - რა ხდება orphan ან ambiguous mapping-ის დროს?

  ### ფაილის lifecycle

  RECEIVED
  → VALIDATING
  → ACCEPTED
  → QUARANTINED
  → SNAPSHOT_MEMBER
  → PUBLISHED
  → SUPERSEDED
  → RETIRED

  დასადგენია:

  - რომელი სტატუსი აძლევს API-ში გამოჩენის უფლებას;
  - როგორ ხდება version supersede;
  - როგორ ბრუნდება წინა ფაილზე rollback-ისას;
  - შეიძლება თუ არა published artifact-ის წაშლა.

  ### Integrity და validation

  - SHA-256 checksum;
  - MIME/type validation;
  - file-size limit;
  - malware scanning;
  - encrypted/corrupted file handling;
  - archive bomb და path traversal protection;
  - checksum-ის ხელახალი verification download-ისას;
  - row-count და file-count reconciliation.

  ### Upload reliability

  - resumable/multipart upload;
  - retry და idempotency key;
  - partial upload cleanup;
  - network failure recovery;
  - duplicate re-upload-ის ქცევა;
  - ერთ პაკეტში 1000 row/1500 file-ის transaction boundary;
  - რა ხდება, თუ 1500 ფაილიდან 3 ვერ აიტვირთა.

  ### Contract და snapshot

  - ფაილის კავშირი contract revision-თან;
  - dataset version;
  - immutable snapshot;
  - snapshot-ში მხოლოდ სრულად validated artifact-ები შედის;
  - partial package არ უნდა გამოქვეყნდეს;
  - Access artifact, object manifest და DB rows ერთ revision-ზე უნდა იდგეს.

  ### Security და privacy

  - ვინ ხედავს artifact-ს;
  - ვინ ხედავს metadata-ს;
  - tenant/site/product isolation;
  - field-level და file-level policy;
  - signed URL-ის ვადა;
  - URL-ის ერთჯერადობა ან download limit;
  - sensitive file-ის redaction/quarantine;
  - audit trail: ვინ ატვირთა, ვინ ნახა, ვინ ჩამოტვირთა.

  ### Retention და archive

  - retention policy;
  - legal hold;
  - archive copy;
  - superseded version retention;
  - purge authorization;
  - disaster recovery restore;
  - object-lock/versioning policy.

  ### API behavior

  - metadata response და file download ცალკე endpoint-ებია;
  - API არ აბრუნებს raw storage path-ს;
  - 404, 403, 409, 410, 422 შემთხვევების მკაფიო semantics;
  - pagination attachments-ზე;
  - per-include limits;
  - ETag და conditional download;
  - content negotiation;
  - download audit event.

  ### ოპერაციული კონტროლი

  - orphan-object scanner;
  - orphan-row scanner;
  - missing-object scanner;
  - checksum drift detector;
  - stale upload cleanup;
  - storage quota;
  - metrics/traces/log correlation;
  - alerting failed upload/reconciliation-ზე.

  ყველაზე მნიშვნელოვანი დამატებითი კითხვა არის:

  > თუ მონაცემი სწორია, მაგრამ ფაილი აკლია, ან ფაილი სწორია, მაგრამ row-სთან კავშირი გაურკვეველია — სისტემა გამოაქვეყნებს, ნაწილობრივ გამოაქვეყნებს თუ მთლიან პაკეტს quarantine-ში გადაიყვანს?

  ჩვენი cardinal წესით სწორი პასუხია:

  ambiguous or incomplete binding
  → fail-closed
  → quarantine
  → explicit issue
  → no publication

  ეს კითხვები უნდა გახდეს generic Artifact Attachment Contract-ის ნაწილი, რათა იგივე მოდელი იმუშაოს KIDS-ის, სხვა site-ის, სხვა provider-ისა და ნებისმიერი ფაილური data-product-ისთვის.
