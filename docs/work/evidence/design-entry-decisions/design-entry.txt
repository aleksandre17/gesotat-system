1. DECISIONS - what the evidence changed
------------------------------------------------------------------------------

ADR-014  Two programs, one authority plane                        [PROPOSAL ADOPTED + 3 additions]
  Validated against ONE FACT -> ONE OWNER (the two programs own different facts) and
  STATE != WORK (a merged lifecycle would put increment-level work into MANIFEST).
  Three alternatives rejected on evidence; parent/child fails because the child is AHEAD
  of the parent - implementing while the parent forbids implementation.
  Added beyond the proposal: a conflict protocol; the meta-level cut (M1-and-below vs
  M2/M3) that makes the split checkable; and a REVIEW CONDITION, without which an
  explicit split is unbounded temporary architecture at programme scale.

ADR-015  SDMX conformance boundary                                [PROPOSAL REFRAMED]
  Finding 1: Q47 in the statistical domain register ALREADY decides the conformance claim
    (Information Model 3.1 subset; SDMX-CSV 2.0; SDMX-JSON 2.0; conformance matrix;
    official schema validation; multi-measure -> 2.1 rejected, no silent pivot).
    Writing a second claim would have created duplicate authority, so it is adopted by
    reference and this ADR owns only the boundary.
  Finding 2: SDMX declares conformance per artefact class and interface, not as ranked
    levels - so 'which level?' has no answer in the standard. Sections: 1 Framework,
    2 Information Model, 5 Registry, 6 Technical Notes, with REST API / SDMX-ML /
    SDMX-JSON / SDMX-CSV maintained separately; current version 3.1 (May 2025), which is
    what S1/Q47 already pin. Confidence MEDIUM-HIGH: the 3.1 PDF text layer was not
    extractable in this environment; no part of the decision depends on exact wording.
  Boundary rule, mechanically applicable: a responsibility is inside the SDMX boundary if
    and only if its data is an observation set keyed by a declared dimension tuple.
  Out of scope and said so: entity/relation/resource/geo families, the serving API, the
    control plane, canonical persistence, VTL, provider and operational lifecycle.
  Banned as a claim: 'SDMX-compatible' / 'SDMX-like' / 'SDMX-shaped'.

ADR-016  Access: supported provider, no semantic authority        [PROPOSAL ADOPTED + 1 distinction]
  The binary was rejected: PERMANENT licenses provider limits to shape canonical
  semantics; TRANSITIONAL licenses neglect of a provider carrying live work.
  Seven rules, each with the test that makes it enforceable.
  Added beyond the proposal: Access is THREE responsibilities - physical provider,
  authoring surface, round-trip carrier - and only the first is about a database. The
  platform's real dependency is an offline typed authoring surface, of which Access is
  today's implementation. Also recorded: rules 3-5 are unenforceable until provider
  capability has exactly one producer (CF-038 three authorities, RC-003 no producer).
