1b. THE TWO REVIEW FALSIFICATIONS - claims corrected, not defended
------------------------------------------------------------------------------

  R-8 grain digest correspondence            ARCH-CANONICAL 31.6
     claim under review : "declared grain uniqueness is ENGINE-ENFORCED by
                          UNIQUE(structure_revision_id, business_key_digest), digest per Q39"
     falsification      : a unique index over a digest proves invariant A - two identical
                          digests cannot coexist. It does NOT prove invariant B - that the
                          digest is the digest of the record's ACTUAL persisted grain values.
                          Grain values live across typed value-domain tables; nothing in the
                          draft stopped a writer persisting values X alongside digest(Y).
     engine analysis    : B cannot be declarative in SQL Server 2022.
                          CHECK cannot reference another table. A persisted computed column
                          cannot leave its own row. A FOREIGN KEY cannot compute a hash. An
                          indexed view cannot assemble a multi-row tuple into one hashable row
                          (no STRING_AGG, no HASHBYTES over an aggregate, no subqueries).
                          UNIQUE over the values themselves requires the grain in ONE row,
                          i.e. a per-structure table - exactly what the stable kernel forbids.
                          => FULL DECLARATIVE ENFORCEMENT IS IMPOSSIBLE WITHOUT DEFEATING
                             THE STABLE-KERNEL REQUIREMENT. Stated, not engineered around.
     mechanism adopted  : L1 GENERATED, NEVER ACCEPTED - no role holds INSERT/UPDATE on
                             platform.record; the sole write path has NO digest parameter
                          L2 DERIVED IN-TRANSACTION - the procedure's last statement and an
                             AFTER trigger on each value table recompute from PERSISTED rows
                          L3 VERIFIED BY TRIGGER - tr_record_grain_digest_verify recomputes
                             and THROWs on mismatch; XACT_ABORT ON -> full rollback
                          L4 RECONCILIATION - out-of-band recompute-and-compare, the detective
                             control for a disabled trigger
     Q39 WITHDRAWN      : Q39 canonicalizes a CONTRACT JSON DOCUMENT with RFC 8785 JCS and NFC
                          on the JVM. A trigger cannot recompute it. Reusing it would have
                          forced either a SECOND JCS IMPLEMENTATION IN T-SQL - a parallel
                          canonicalizer, forbidden - or the loss of L2/L3, collapsing B to
                          application-only. The grain key is therefore an ENGINE-LOCAL
                          encoding: ordinal || domain_tag || len32 || canonical_bytes per
                          component in declared order, length-prefixed (injective), then
                          HASHBYTES SHA2_256 -> BINARY(32). Q39 keeps its own scope.
     authority boundary : the ordered declared grain-component tuple is the SEMANTIC AUTHORITY.
                          The digest is a PHYSICAL enforcement/indexing representation only -
                          never published, never exchanged, never a business identifier, never
                          compared across systems. Proof it is not semantic: changing the
                          encoding is a physical migration that rebuilds every digest and
                          changes no meaning.
     residuals named    : (1) a DDL-privileged principal can DISABLE TRIGGER - identical to the
                              enforcement class of all 20 existing immutability triggers, so
                              not a regression; controls are DDL audit + L4
                          (2) Unicode NFC of text grain components - byte-exact hashing admits
                              NFC and NFD forms as distinct grain; T-SQL cannot normalize.
                              OWNER DECISION REQUIRED (ARCH-CANONICAL 39)
                          (3) a record written before its grain rows - closed by write-path
                              ordering and business_key_digest NOT NULL
     corrected verdict  : INV-006 = PARTIAL. A declarative, B procedural-in-engine.
                          Against the baseline, where INV-006 is APPLICATION-ONLY, this is
                          still a strengthening - but the earlier unqualified claim was false.

  R-9 cardinality-specific enforcement       ARCH-CANONICAL 31.7
     claim under review : "declared cardinality compiles into the uniqueness constraint over
                          the endpoint tuple"
     falsification      : UNIQUE(rel, source, target) prevents duplicate PAIRS. That is the
                          whole rule for MANY_TO_MANY and NONE of the rule for the other three:
                          it admits a second parent under ONE_TO_MANY, a second target under
                          MANY_TO_ONE, and both under ONE_TO_ONE. One rule was named for four
                          semantics.
     second problem     : the obvious fix - a per-relationship filtered index - is DDL PER
                          RELATIONSHIP, which would defeat
                          ORDINARY_NEW_RELATIONSHIP_REQUIRES_PLATFORM_DDL: NO. Rejected.
     derivation         : two independent questions decide the rule -
                          may a given b have more than one a?  if not, TARGET must be unique
                          may a given a have more than one b?  if not, SOURCE must be unique
                          ONE_TO_ONE   -> both roles unique
                          ONE_TO_MANY  -> target unique  (a child cannot gain a second parent)
                          MANY_TO_ONE  -> source unique  (the inverse)
                          MANY_TO_MANY -> pair unique only
     mechanism adopted  : THREE FIXED INDEXES, ZERO PER-RELATIONSHIP DDL
                          cardinality_code stays the semantic authority (closed vocabulary,
                          CHECK - preserving R-4). Two PERSISTED computed BIT flags project it
                          on the declaration row; the instance row carries the same two flags
                          FK-LOCKED by a composite FOREIGN KEY, so they cannot disagree.
                            ux_rel_pair       (rel, source, target)
                            ux_rel_source_one (rel, source) WHERE enforce_source_unique = 1
                            ux_rel_target_one (rel, target) WHERE enforce_target_unique = 1
     proven in-repo     : the live catalogue already carries filtered indexes with exactly
                          these predicate forms -
                            ux_statistical_contract_draft_approved  WHERE state_code='APPROVED'
                            ux_api_operation_owner_idempotency      WHERE idempotency_key IS NOT NULL
                          single equality to a literal; no OR and no computed column in the
                          predicate, both of which SQL Server forbids there.
     bonus properties   : the composite FK makes the ENGINE REFUSE an in-place cardinality
                          change while rows exist (it becomes a new revision + migration, which
                          is the contract semantics anyway); endpoint STRUCTURE conformance
                          uses the identical device.
     corrected verdict  : all four cardinalities ENGINE-ENFORCED DECLARATIVELY, with typed
                          endpoints, real FKs, zero cascade and contract authority intact.
                          CF-040 closes for four cardinalities rather than one.

2. THE ARCHITECTURAL RESULT
------------------------------------------------------------------------------

  STABLE PHYSICAL KERNEL (value-domain-partitioned typed tables)
     + LOGICAL MODEL EVOLVING BY DECLARATION
     + SELECTIVE, DECLARED, REVERSIBLE MATERIALIZATION

  Derived from evidence rather than preference: the repository already answers the
  dynamic-model question three times - observation/observation_dimension (typed, grain
  unenforceable), entity_record.payload_json (untyped: CF-039), and localized_text /
  resource_locator / entity_classification (typed, keyed, constrained). The third is the
  strongest, and it is what the kernel generalizes.

  Why it is not EAV - three checks any reviewer can apply:
     1. each value table holds ONE value domain with its correct physical type
     2. the component identifier is CONTRACT-GOVERNED, never free text
     3. the primary key INCLUDES the component and its discriminator
  A design that loses any one of the three IS EAV and is rejected.

  Grain enforcement, stated correctly after review (R-8):
     invariant A - no two identical grain tuples -> UNIQUE(structure_revision_id,
                   business_key_digest). ENGINE, DECLARATIVE.
     invariant B - the digest matches the actual persisted values -> generated-not-accepted,
                   derived in-transaction, verified by trigger. ENGINE, PROCEDURAL.
     Today INV-006 is application-only, so this remains a STRENGTHENING - but it is PARTIAL,
     not the "engine-enforced by construction" claimed before review.

3. WHAT GENUINELY WEAKENS - named, not hidden
------------------------------------------------------------------------------

  Per-field NOT NULL      -> compiled validation in the generic kernel
  Per-field range/pattern -> compiled validation, or engine when materialized

  Why this regresses nothing that exists: all 115 live CHECK constraints and every existing
  NOT NULL sit on PLATFORM KERNEL tables, which remain physical with their constraints
  intact. No user dataset has a physical range CHECK today, because no user dataset has its
  own table - observation and entity_record are already generic. The comparison is therefore
  generic-and-typed versus generic-and-untyped, and the revised design wins it.

  Bounded by the specialization criteria of ARCH-CANONICAL 31.4 - volume, query plan,
  regulatory enforcement, provider round trip. A materialization changes performance and
  never meaning, and dropping it is safe: that reversibility is what separates specialization
  from schema proliferation.

  A THIRD limitation, of a different kind, is added by R-8 and kept out of the list above so
  the two value-constraint limitations accepted by review are not silently widened:
  tuple-to-digest correspondence is procedural, not declarative (31.6), with its three named
  residuals.
