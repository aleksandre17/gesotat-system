# Standards profile and design sources

Reviewed 2026-09-20 against primary sources. Versions below are deliberate references, not claims to track every latest release. Do not upgrade runtime dialects merely because a newer specification exists; make compatibility decisions in approved contracts/ADRs. Local requirements are the project's interpretation; no external certification is asserted.

**Disposition vocabulary (added 2026-09-21, `PHASE-002` / `GATE-STANDARDS`).** Every source carries exactly one disposition, because "listed" is not a decision:

- `ADOPT` — used as specified, within the stated subset.
- `ADAPT` — the concepts are used; the artifact form, serialization or conformance requirement is not.
- `CONDITIONAL` — not in force until its named condition is met; the condition is stated, never "later".
- `REJECT` — deliberately not adopted, with the reason. A rejection is a decision and is recorded so it is not silently re-litigated.

## Domain profiles — where domain-specific standards actually live

A **platform profile** (this file) fixes what applies everywhere. A **domain profile** selects and narrows it for one family of decisions. Both are required; neither may contradict the other.

| Domain | Profile | Owns |
|---|---|---|
| Statistical contract | `docs/work/STATISTICAL-CONTRACT-OPEN-QUESTIONS.md` §7 (`S1…S16`) | the standards bound to decisions `Q01…Q50`: SDMX versions and cross-domain codelists, ISO 8601 usage, exact-numeric avoidance of IEEE 754, SemVer application, JSON Schema dialect, JCS/SHA-256/NFC canonicalization, HTTP conditional-request and idempotency headers, ABAC and separation of duties, GSIM/GSBPM/ISO-11179 vocabulary, PROV-O and Trace Context usage, outbox and expand/contract patterns |

**Precedence rule.** Where both profiles name the same standard, the platform row fixes the disposition and the pinned reference; the domain row fixes its *application* to specific decisions. **A domain profile may narrow a platform adoption; it may never adopt something the platform profile rejects, nor weaken a platform limit.** A domain profile that needs an unadopted standard raises it here first.

**Classification resolved 2026-09-21.** The statistical domain profile was classified `SUPPORTING` while describing itself as a design authority, and it is the only home of `S1…S16`. `ADR-014` (two programs, one authority plane) establishes that a program owns its domain profile under this platform profile, and `docs/project/ADOPTION.md` §4 now classifies `docs/work/STATISTICAL-CONTRACT-OPEN-QUESTIONS.md` **`CANONICAL` for the statistical domain's decisions and standards, and for nothing else**. It states no project state and declares no rehabilitation gate. The SDMX **boundary** — which responsibilities SDMX may shape at all — is `ADR-015`; the conformance **claim** remains `Q47`'s.

**Investigated 2026-09-21 and deliberately not adopted, recorded so the question is not reopened blindly:** GSBPM as a process model (named above), DAMA-DMBOK (a body of knowledge, not a specification), data-product description specifications such as ODPS/DPDS (too immature, and tied to a mesh topology this platform does not have), and CIDOC-CRM (a different domain). Each was considered against a responsibility this platform actually has; none earned a hook.

Choose domain-specific standards (for example statistical exchange or geospatial vocabularies) through the existing domain contracts, and register the profile above so it is reachable. Never infer that adding a standards name proves implementation. Record exact version, adopted subset, mapping, unsupported features and conformance evidence before making interoperability claims.
